# WhatsApp Visible Status extraction contract

Research for [issue #110](https://github.com/zytact/GramGrab/issues/110), observed on 2026-08-05.

## Decision

GramGrab can establish a narrow `visible-status-v1` contract around the one photo or video already open in WhatsApp Web. The contract should describe an atomic observation, not a WhatsApp collection and not a durable WhatsApp identity.

The extractor should return exactly one of:

```ts
type VisibleStatusObservation =
  | { tag: 'not-visible'; reason: 'wrong-origin' | 'viewer-absent' }
  | { tag: 'unsupported'; reason: 'text' | 'sticker' | 'unknown-media' }
  | { tag: 'not-ready'; reason: 'media-loading' }
  | { tag: 'format-changed'; shape: RedactedShape }
  | {
      tag: 'ready';
      version: 1;
      observedAt: number;
      captureId: string;
      media: {
        kind: 'photo' | 'video';
        mimeType: string;
        byteLength: number;
        width: number;
        height: number;
        durationMs?: number;
      };
      attribution: { displayName: string; caption?: string };
      leaseExpiresAt: number;
    };
```

The actual media bytes or page-local handle belong to the page-to-extension boundary in issue #111, not this public observation shape. `captureId` must be generated by GramGrab for this extraction attempt. It must not be a WhatsApp message ID, contact ID, media key, hash, or URL.

## Why this is the reliable minimum

### Eligibility

A Status is eligible only when all of these conditions hold in one top-level `https://web.whatsapp.com/` document:

1. The active Status player is present.
2. Exactly one supported foreground candidate is present inside that player.
3. The candidate is either the primary photo or the video, has non-zero intrinsic dimensions, and its bytes are ready.
4. The same player and media element still identify the Visible Status after byte acquisition completes.

Do not open the Status drawer, click a Status row, enumerate neighboring rows, or invoke WhatsApp's next/previous handlers. The parent specification expressly limits the feature to the photo or video Status the person opened and excludes adjacent enumeration [S1]. This also avoids promising control over view receipts.

### Media form

The live photo player contained two large images: a low-resolution `data:` image used as presentation backing and a high-resolution `blob:` image used as the foreground photo [L2]. The video player contained one large `<video>` with a `blob:` source and poster, finite duration, intrinsic dimensions, and the stable player marker `status-video` [L1]. Therefore:

- Photo selection must choose the foreground media inside the active player, not the first or largest image on the page and not the `data:` backing image.
- Video selection must choose the player video, not its poster.
- The extractor must resolve the selected resource into an owned immutable byte snapshot before reporting `ready`. A page `blob:` URL is a temporary observation detail, never part of the returned or persisted contract.

`kind`, MIME type, byte length, intrinsic width and height are required. Duration is required for video and forbidden for photo. Caption and display name are presentation metadata only. Missing caption is valid. No contact identifier is needed for the stated product behavior.

### Identity and advancement

Identity has two scopes:

- During capture, use a page-local guard consisting of the exact player node, exact foreground media node, and its current source value. This guard is never serialized.
- After capture, use a fresh GramGrab `captureId` or Operation ID. Do not derive durable identity from WhatsApp internals.

This distinction is necessary because WhatsApp exposes private player indexes, session IDs, message models, and Status models in the current React tree [L3], but these are undocumented implementation details and include personal identifiers. They are useful evidence that WhatsApp tracks a current item, but they are not a safe compatibility contract.

Automatic advancement is a real race. In a bounded observation of an already-viewed video, the foreground media node changed and the player closed before the media element emitted `ended` [L4]. Capture must therefore be optimistic and atomic:

1. Record the page-local guard.
2. Acquire and validate the bytes.
3. Re-read the active player and foreground candidate.
4. If any guard component changed or the player disappeared, discard the bytes and return `not-visible` or a dedicated `visible-status-changed` acquisition failure.

Never silently return the next Status.

### Expiry

The stable DOM does not expose an authoritative Status expiry. The current private Status model contains a numeric expiry field [L3], but depending on it would make a private, identifier-bearing WhatsApp model part of GramGrab's compatibility surface.

The reliable contract is therefore:

- Eligibility is true only at `observedAt` and must be revalidated during capture.
- `leaseExpiresAt` is GramGrab's short-lived transfer lease, not a claim about WhatsApp's upstream expiry. The repository already uses a 60-second workspace transfer TTL [S3].
- Once bytes are owned by GramGrab, later upstream expiry does not invalidate that in-flight operation.
- History may retain non-sensitive download facts, but must not retain the Status bytes for direct redownload, consistent with the parent specification [S1].

If product copy needs an exact upstream expiry time, this contract cannot supply it reliably and that requirement should be rejected rather than inferred from private fields or relative UI text.

### Format-change detection

Treat the WhatsApp DOM as a strict adapter input:

- Scope every lookup to the active Status player.
- Require exactly one recognized foreground candidate and exact media invariants.
- Reject ambiguous image pairs, missing player markers, zero dimensions, MIME/kind disagreement, multiple foreground candidates, or a changed capture guard.
- Return `format-changed` with only a redacted structural shape: element tags, allowed attribute names, candidate counts, protocols, and value types. Never include text, URLs, IDs, hashes, keys, or byte content.
- Do not fall back to scanning the whole WhatsApp document. The idle Status drawer in the live session contained more than one hundred unrelated images, including avatars, thumbnails, and tiny placeholders [L0].

The adapter may use current first-party markers such as `status-player-uie`, `status-video`, `status-progress-bar-segment`, and `status-player-contact-name` [L1], but must assume they can change. A missing marker is a loud format change, not "no media."

## Repository implications

The repository currently defines Status only as an ephemeral WhatsApp media item [S2]. Its workspace acquisition union supports only Instagram source and Instants acquisition, while its media item already has the basic type, URL, dimensions, and attribution-shaped fields [S3]. The manifest currently has no WhatsApp host permission and no declared content script [S4]. This research does not choose how temporary page access or media transfer should work; those decisions belong to issue #111.

The extraction adapter should remain browser-extension-only and produce a new WhatsApp acquisition variant rather than pretending a Status is an Instagram Source.

## Live evidence, redacted

The live session was inspected passively except for opening two already-viewed Status items. The drawer reported no unviewed updates before either item was opened. Videos were paused during inspection. The viewer was closed after observation. No screenshots, media, names, text, identifiers, URLs, keys, hashes, or decrypted payloads were saved.

- **L0 - idle Status drawer:** no active player; 133 image elements across the application; Status drawer markers and 14 visible Status rows were present.
- **L1 - video Status:** active `status-player-uie`; one large `<video>` with `blob:` source, poster, finite duration, non-zero intrinsic dimensions, and `status-video`; non-empty contact-name and subtitle elements were present without reading their values.
- **L2 - photo Status:** active `status-player-uie`; one low-resolution `data:` presentation image and one high-resolution `blob:` foreground image; one progress segment.
- **L3 - private model shape:** the player React props exposed `msgIdx`, `rowIdx`, `totalMsgs`, `statusIsUnread`, navigation callbacks, a media model with type/MIME/dimensions/duration/size/blob fields, and a Status model with count/unread/expiry fields. Values capable of identifying a person or item were not retained.
- **L4 - lifecycle:** during a 28-second bounded observation of an already-viewed video with about 24 seconds remaining, the media node changed once and the player disappeared before the original video emitted `ended`.

These observations describe one WhatsApp Web build and are evidence for invariants and failure handling, not a promise that its private names remain stable.
