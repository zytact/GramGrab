# WhatsApp Visible Status verification without personal fixtures

Research for [Prove WhatsApp support without personal fixtures](https://github.com/zytact/GramGrab/issues/114), based on GramGrab at `7f4d844`, the adopted WhatsApp decisions, and primary browser sources. This note defines the evidence required before support may be claimed. It does not authorize collecting live-session fixtures or performing live inspection during implementation.

## Decision

WhatsApp support is proven only by both parts of this strategy:

1. deterministic synthetic tests prove GramGrab's extraction, transfer, failure, lifetime, and non-retention contracts without WhatsApp data; and
2. a human runs the same small structural acceptance matrix with the built Chromium and Firefox packages to prove that the current WhatsApp Web player still exposes the adopted foreground media to an isolated-world controller in each browser.

Synthetic tests are authoritative for all behavior GramGrab owns. Live evidence is required only for facts a synthetic DOM cannot establish: current player-shape compatibility, isolated-world access to the page-owned `blob:` source, actual `activeTab` injection and tab/frame port behavior, and visible Chromium/Firefox parity. A live pass cannot replace a missing synthetic invariant, and a Chromium pass cannot stand in for Firefox.

The strategy verifies the decisions already made in:

- [Establish the Visible Status extraction contract](https://github.com/zytact/GramGrab/issues/110#issuecomment-5195700504): one already-visible photo or video, guarded by the exact player node, foreground media node, and current source through post-acquisition revalidation;
- [Choose the WhatsApp page-to-extension media boundary](https://github.com/zytact/GramGrab/issues/111#issuecomment-5230704902): popup-owned injection into the main frame's default isolated world, a tab-bound port, and bounded ordered base64 chunks with acknowledgements;
- [Define WhatsApp acquisition privacy and security constraints](https://github.com/zytact/GramGrab/issues/113#issuecomment-5204052391): `activeTab` plus `scripting`, no WhatsApp host permission, in-memory-only handling, an independent approximately 60-second retention ceiling, receipt-only History, and structural-only diagnostics; and
- [Integrate WhatsApp acquisition failures and diagnostics](https://github.com/zytact/GramGrab/issues/112#issuecomment-5207796764): the seven acquisition Failure codes and their recovery and diagnostic policies.

## Why the evidence split is sufficient

Chrome's extension guidance separates unit tests with mocked extension APIs from end-to-end tests that load an extension in a browser, and recommends asserting observable behavior rather than private extension state ([unit testing](https://developer.chrome.com/docs/extensions/how-to/test/unit-testing), [end-to-end testing](https://developer.chrome.com/docs/extensions/how-to/test/end-to-end-testing)). GramGrab already has browser API mocks in `apps/extension/src/test/setup.ts`, popup integration tests in `apps/extension/src/integration.test.tsx`, background-listener tests in `apps/extension/src/background.test.ts`, and generated-manifest tests in `apps/extension/src/manifest.test.ts`. The WhatsApp suite should extend those boundaries with invented page states and generated bytes rather than captured WhatsApp artifacts.

The browser mechanics are intentionally the least-capable common contract:

- `activeTab` grants temporary host access after a user invocation and is revoked when the tab navigates away or closes ([Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [MDN activeTab](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/permissions#activetab_permission)).
- `scripting.executeScript()` requires `scripting` plus host permission or `activeTab`; its target defaults to the main frame when no frame IDs or all-frames option is supplied, and `ISOLATED` is the default execution world ([Chrome scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting#method-executeScript), [MDN executeScript](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/executeScript)).
- `tabs.connect()` can target a specific frame and returns a `Port`; navigation or frame teardown disconnects the channel ([Chrome tabs.connect](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-connect), [MDN tabs.connect](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/tabs/connect)).
- Chrome extension messaging uses JSON serialization while Firefox uses the structured clone algorithm, so portable envelopes must remain JSON-compatible ([Chrome messaging](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#serialization), [Mozilla Chrome incompatibilities](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Chrome_incompatibilities#data_cloning_algorithm)).
- Fetch exposes response bodies as streams and aborting the associated request aborts consumption of the response body ([Fetch Standard](https://fetch.spec.whatwg.org/#dom-body-body), [Fetch Standard abort steps](https://fetch.spec.whatwg.org/#dom-abortcontroller-abort)).

These sources establish that the chosen mechanism exists in both browser families. Only the live matrix can establish that the current WhatsApp `blob:` resource is actually readable through that mechanism in both built packages. If either browser disproves that assumption, support is unproven. The result is not permission to add a MAIN-world bridge or host permission.

## Automated synthetic suite

All fixtures must be authored from scratch. Use labels such as `STATUS_A`, generated image/video test cards, deterministic byte arrays, and fake `blob:` URLs created by the test harness. Never copy a DOM fragment, attribute value, URL, response, identifier, name, caption, key, media hash, or byte sequence from WhatsApp.

Where the implementation returns Effect programs, use Effect-aware tests and a test clock rather than wall-clock sleeps. `@effect/vitest` provides `it.effect` with the test environment and `it.effect.prop` for Effect-based property tests; its vendored primary implementation is under `.repos/effect/packages/vitest/`. Schema inputs should be decoded from `unknown`, and failures should be asserted by their tagged Failure code rather than free-form messages.

### 1. Extraction contract

Build a minimal synthetic document for exactly one foreground player. Table-drive these cases:

| Synthetic state                                                                           | Required result                                         |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| One ready foreground `blob:` photo plus a backing `data:` image                           | Capture the foreground photo only                       |
| One ready active `<video>` plus its poster                                                | Capture the video only                                  |
| No active player                                                                          | `WHATSAPP_STATUS_NOT_VISIBLE`                           |
| Text, sticker, link preview, or other non-photo/video item                                | `WHATSAPP_STATUS_UNSUPPORTED`                           |
| Supported media still loading within the bounded wait                                     | Continue waiting without changing identity              |
| Supported media never becomes ready                                                       | `WHATSAPP_STATUS_NOT_READY`                             |
| Player-like structure with a missing, duplicate, malformed, or unknown required invariant | `WHATSAPP_FORMAT_CHANGED` with structural evidence only |
| Adjacent Status rows or unrelated document images                                         | Never enumerate or return them                          |

For every ready photo and video, capture the exact player node, foreground media node, and source value as a non-serializable page-local guard. Mutate each guard component independently before fetch, between chunks, before completion, and immediately before post-acquisition revalidation. Any mutation or player disappearance must discard all acquired bytes and produce `WHATSAPP_STATUS_CHANGED`. It must never issue `captureId`, create a download, or silently bind to the replacement Status. An unchanged guard produces exactly one immutable snapshot and only then receives a fresh GramGrab `captureId`.

Also spy on page interactions. Extraction fails its contract if it clicks, advances, opens the viewer, reads adjacent rows, calls private page functions, or reads contact text or private runtime models.

### 2. Page-owned blob acquisition

Provide a fake `blob:` fetch adapter backed by generated bytes and a controllable `ReadableStream`. Cover:

- photo and video bodies delivered in one, two, and many chunks;
- chunk boundaries at zero, one byte, the configured chunk maximum, and one byte over that maximum;
- empty body, unsafe or kind-mismatched MIME classification, aggregate size exactly at and one byte above the ceiling;
- source revocation before fetch, fetch rejection, truncated stream, reader failure, and an unexpected producer failure;
- cancellation before the first read, while a read is pending, after a chunk, and during completion; and
- guard change while the stream is active and after the final byte but before snapshot acceptance.

Assert exact reconstructed bytes, media metadata, and final download input only in these synthetic tests. Chunk sizes and aggregate ceilings are implementation constants, not facts learned from a live file.

### 3. Port protocol and backpressure

Drive the real schemas and state machine through paired fake ports. Every envelope must be decoded from `unknown` through a closed schema. Cover:

- the expected protocol version, request identity, media kind, sequence, declared decoded length, payload, completion, acknowledgement, cancellation, and terminal envelopes;
- ordered chunks with one acknowledgement opening only the configured next window;
- duplicate, skipped, reordered, replayed, late, or post-terminal chunks and acknowledgements;
- malformed base64, decoded-length mismatch, per-chunk overflow, aggregate overflow, wrong protocol version, wrong request, wrong tab, and wrong frame;
- disconnect before metadata, mid-chunk, after the final chunk but before revalidation, and after a terminal result;
- sender, receiver, and simultaneous cancellation, each idempotent; and
- a sender that attempts to read ahead beyond the acknowledgement window.

Positive tests must show that bounded ordered chunks reconstruct the generated payload exactly. Negative tests must show that partial bytes are unreachable after termination, no `captureId` is issued, no download starts, listeners are removed, and each owned URL is revoked at most once.

Property tests should generate JSON-compatible envelope sequences and assert the protocol laws: at most one terminal result, monotonic accepted sequence, no acceptance beyond the acknowledgement window, aggregate length never above the ceiling, and no state transition out of terminal. This targets ordering and replay combinations that example tests can easily miss.

### 4. Ownership, cancellation, and retention

Use independent test clocks for Status-guard invalidation and the approximately 60-second retention ceiling. Prove they do not reset or cancel one another. Exercise immediately before, exactly at, and after the ceiling for:

- an active stream;
- a completed in-memory snapshot awaiting download acceptance;
- an extension-created object URL;
- popup close, tab close, tab navigation, port disconnect, schema failure, size failure, extraction failure, download rejection, and success; and
- a late producer or browser callback after cleanup.

Every path must abort both ends idempotently, discard partial or completed in-memory bytes when ownership ends, remove listeners, and revoke extension-owned object URLs. The popup owns the operation. Tests must prove that no service-worker global, workspace transfer, `storage`, IndexedDB, OPFS, or page-created `blob:` URL is required for correctness.

### 5. Failure and outcome contract

Exhaustively map acquisition states to the adopted seven item-scoped Failure codes:

| Failure code                  | Synthetic trigger                                                                                                | Diagnostic policy        |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `WHATSAPP_PAGE_ACCESS_FAILED` | wrong origin after invocation, navigation, tab close, lost grant, injection rejection, or tab/frame port failure | structural               |
| `WHATSAPP_STATUS_NOT_VISIBLE` | no active player                                                                                                 | none                     |
| `WHATSAPP_STATUS_UNSUPPORTED` | visible unsupported media kind                                                                                   | none                     |
| `WHATSAPP_STATUS_NOT_READY`   | readiness wait expires                                                                                           | none                     |
| `WHATSAPP_STATUS_CHANGED`     | guarded player, media node, or source changes or disappears                                                      | none                     |
| `WHATSAPP_FORMAT_CHANGED`     | strict player invariant no longer matches                                                                        | structural, copy offered |
| `WHATSAPP_ACQUISITION_FAILED` | unexpected acquisition-boundary failure after known cases are exhausted                                          | structural, copy offered |

One explicit capture click allocates `operationId`; `captureId` remains absent until successful byte acquisition and guard revalidation. The outcome stays `pending` until the browser accepts the download request, then becomes `started`. Every acquisition failure after the click is item-scoped `failed`. Retry requires another explicit click, retains `operationId`, creates a fresh request identity and `activeTab` grant, and never silently captures the currently visible replacement.

Test every producer against schema, normalization, presentation, recovery, diagnostics, and History policy. Do not add a public transfer phase or transfer Failure code. Low-level port and stream failures normalize to `WHATSAPP_PAGE_ACCESS_FAILED`, `WHATSAPP_STATUS_CHANGED`, or `WHATSAPP_ACQUISITION_FAILED` according to their meaning.

### 6. Privacy by construction

Schema and type tests must make the WhatsApp diagnostic branch incapable of carrying arbitrary strings, records, causes, stacks, MIME strings, filenames, URLs, IDs, attributes, or payloads. Runtime tests must reject excess properties and prove that only closed structural enums, bounded counts, versions, browser family/major version, safe phase, Failure code, invariant code, lifecycle booleans, and an epoch capture time can survive.

For every success and failure path, inspect all observable outputs and durable stores. The only allowed History receipt is exactly `{ source, mediaKind, timestamp, savedFilename, outcome }`. It has no thumbnail, re-download handle, WhatsApp identifier, `captureId`, URL, key, or payload. The saved filename must use a name-free descriptor and timestamp. The workspace must have no WhatsApp capture surface or handoff state.

Popup tests must also prove that export modes requiring persistent temporary media are unavailable for WhatsApp and are presented as an explicit limitation. No hidden or direct route may submit a WhatsApp capture to those modes.

Add a repository policy test that rejects WhatsApp domains, URL query credentials, phone-number-like identifiers, forbidden identifier/key fields, long unexplained base64, captured DOM/HTML, and unapproved binary fixtures. This is defense in depth. It does not make captured data safe to commit.

Test failure output itself: assertions and reporters may print only scenario labels, symbolic Failure codes, closed invariant values, and booleans. They must never interpolate input envelopes, page structures, URLs, payloads, or thrown browser strings.

### 7. Manifest and built-package checks

For both generated manifests, require:

- `activeTab` and `scripting` permissions;
- no `https://web.whatsapp.com/*` or WhatsApp CDN host permission;
- no registered content script;
- Chromium's service worker and Firefox's generated background-script form; and
- only packaged code passed to `scripting.executeScript()`.

Run the browser-independent synthetic suite against both target builds. Then load each built package in a fresh automation profile. The production popup must reject an invented local page as ineligible. A browser harness may exercise the packaged isolated controller and JSON port protocol against that page without weakening the production origin check. Chrome documents loading an unpacked extension and locating its MV3 service worker with Puppeteer ([Chrome Puppeteer testing](https://developer.chrome.com/docs/extensions/how-to/test/puppeteer)); Mozilla documents temporary installation and `web-ext run` for Firefox development profiles ([Mozilla temporary installation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Your_second_WebExtension#testing_it_out), [web-ext run](https://extensionworkshop.com/documentation/develop/web-ext-command-reference/#web-ext-run)). These browser tests still do not prove WhatsApp compatibility, which belongs to the redacted matrix below.

## Redacted human-run live matrix

The human tester, not the research or implementation agent, performs this procedure. Use two dedicated QA accounts with no personal contacts or chat history. Post only purpose-made image and video test cards containing generic shapes and the labels `STATUS_A` and `STATUS_B`. Do not include a person's name, number, face, voice, location, account identifier, or unique run nonce.

Before each browser run:

1. Build and package the exact commit, calculate the package digest locally, and install it in a fresh browser profile.
2. Record only browser family and version, operating system, build commit, package digest, date, scenario ID, and empty pass/fail fields.
3. Disable screenshots, recordings, HAR capture, console preservation, network export, and any test runner tracing before opening WhatsApp.
4. Open the intended test Status manually. GramGrab must not open it, enumerate other Statuses, or claim anonymous viewing.

Run every row once on current release Chromium and once on current release Firefox:

| Scenario             | Human action                                                                                | Structural pass condition                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| First photo capture  | On the first eligible tab, accept the one-time view-receipt disclosure, click capture once  | One downloaded photo is visibly `STATUS_A`; filename contains no contact name; one receipt has only the allowed fields       |
| Loaded video capture | Open the purpose-made video and click capture once                                          | One playable downloaded video is visibly the intended test card; no poster or adjacent Status is returned                    |
| Advancement race     | Arrange `STATUS_A` immediately before distinct `STATUS_B`, capture near advancement         | Result is `STATUS_A` or `WHATSAPP_STATUS_CHANGED`; `STATUS_B` is never downloaded by that operation                          |
| Lifecycle abort      | Start video acquisition, then close the popup; repeat with tab navigation                   | Operation fails or cancels cleanly; no download, preview, or receipt falsely reports success; reopening starts no operation  |
| Fresh-grant retry    | After an abort or failure, return to the exact intended Status and click again              | Retry requires the new click and captures only the newly visible intended Status                                             |
| Restart and residue  | Complete a capture, delete the download, close the tab and browser, then reopen the profile | No preview, payload, page `blob:` handle, capture handle, or re-download action is recoverable; History remains receipt-only |

For each successful media row, the tester may compare the visible downloaded output with the generic test card in memory and then must immediately delete the download. Do not calculate or record a digest, payload size, source URL, media hash, duration, dimensions, or response metadata from the WhatsApp-delivered file. The durable result records only pass/fail and, on a defined failure, the symbolic Failure code.

Inspect extension storage and diagnostics only through a purpose-built structural inspector that renders allowed key names, closed enum values, bounded counts, and booleans. It must not reveal or export values from arbitrary storage, DOM, exceptions, or network state. Record only `history-shape-pass`, `diagnostic-shape-pass`, `no-recoverable-payload-pass`, and `cleanup-pass` booleans.

After each browser run, delete all downloaded test media, remove the temporary browser profile, and delete the QA Status using the provider's ordinary controls. Do not retain the profile for debugging.

## Evidence and retention rules

The only durable live evidence is a Markdown or JSON result matrix containing:

- browser family/version, OS, date, build commit, and package digest;
- scenario ID;
- pass/fail and an optional symbolic Failure code;
- the four structural cleanup booleans; and
- reviewer initials that are not account identifiers.

Never save or commit WhatsApp media, page or extension screenshots, screen recordings, DOM dumps, HTML, HAR files, request or response headers, network or console logs, browser traces, storage exports, stack traces, free-form browser errors, contact/display data, captions, WhatsApp IDs, media keys, hashes, signed URLs, page `blob:` URLs, decrypted payloads, or downloaded files. Do not capture first and redact later, because the unredacted artifact would already have been retained.

If a failure cannot be explained from the allowed structural result, mark the scenario failed and reproduce it with a synthetic fixture. Do not expand live collection.

## Release gates

Support may be claimed only when all gates pass:

1. all synthetic extraction, protocol, lifecycle, failure, privacy, manifest, and repository-policy tests pass;
2. Chromium and Firefox target packages build and their manifests satisfy the exact permission and no-content-script policy;
3. every live matrix row passes on both current release browser families with the same product outcome;
4. neither browser needs MAIN-world injection, a WhatsApp host permission, persistent storage, workspace handoff, or service-worker lifetime for correctness;
5. every advancement race returns the originally guarded item or `WHATSAPP_STATUS_CHANGED`, never the next item;
6. all live artifacts are deleted and the retained matrix contains only the allowed structural fields; and
7. a reviewer confirms that no prohibited fixture or diagnostic artifact entered the repository or CI output.

Any inaccessible page-owned `blob:` source, format invariant mismatch, browser-only behavior, retained prohibited value, unbounded transfer, missing acknowledgement, cleanup failure, or matrix gap is a failed gate. The honest outcome is "WhatsApp support unproven" until the adopted contract passes unchanged. A failed gate must not be worked around by broadening page access or evidence collection inside this ticket.
